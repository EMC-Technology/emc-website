# 开源目的说明

> 文本全结构化知识系统 — 纯 Rust 知识库基线产品
>
> 项目宪章：使命 — 让全球生态感知纯 Rust 知识库解决方案的可行性，公开验证错误驱动开发和流程驱动开发两大技术哲学；愿景 — 以 Rust 统一完整基础设施闭环，UPCM 驱动包含操作系统在内的所有相关软件；设计哲学 — 0 随机性，0 黑盒推断

## 一、为什么开源

本项目以开源方式发布，核心目的是**让全球生态感知纯 Rust 知识库解决方案的可行性**，并**公开验证两大技术哲学——错误驱动开发和流程驱动开发**。

当前知识库领域被 Python 生态主导（GraphRAG、LlamaIndex、LangChain、Haystack），存在以下结构性问题：

| 问题 | Python 生态现状 | Rust 可提供的解法 |
|------|----------------|-----------------|
| 性能瓶颈 | GIL 限制并发，GC 停顿不可预测 | 零运行时开销，编译时内存安全 |
| 部署复杂 | Docker 镜像 1-5GB，依赖链深 | 单二进制 10-50MB，无运行时依赖 |
| 供应链风险 | pip 依赖链数千包，安全审计困难 | Cargo 锁定 + cargo-deny 供应链审查 |
| 内存安全 | 运行时错误频发（空指针、数据竞争） | 编译时杜绝 UB，所有权系统保证 |
| 一致性保证 | 非确定性结果（GC 时序、async 调度） | 确定性执行，0 随机性，0 黑盒推断 |

然而，"Rust 能否构建完整的知识库系统"这一命题缺乏公开验证。本项目正是这一命题的**首个完整实证**。

### 世界软件生态的两大致命问题

除上述 Python 生态的结构性问题外，本项目开源还旨在揭示并回应世界软件生态中两个更深层、更具普遍性的致命问题：

#### 致命问题一：错误模块不统一

| 问题维度 | 现状 | 后果 |
|----------|------|------|
| 错误类型碎片化 | 每个框架/库/运行时自定义错误类型 | 跨层错误传播需要大量 `map_err`/`From` 样板代码 |
| 错误码无标准 | 各系统自行编号，无统一格式 | 运维无法通过错误码快速定位问题域 |
| 错误链断裂 | 多数错误类型仅保留 `source`，无上下文帧 | 错误传播到上层时丢失原始场景信息 |
| 恢复策略各自为政 | 每个模块独立实现重试/断路/降级 | 无法形成统一的韧性策略 |
| 跨语言/跨运行时不可追踪 | Python↔Rust↔Go 各自的错误模型 | 微服务架构下错误根因分析几乎不可能 |
| 嵌入式/OS 层无统一错误模型 | no_std 环境缺乏标准错误框架 | 从应用到驱动的错误链完全断裂 |

**本项目的回应**：`error-core` crate 展示了统一错误处理的完整范式——四维分类指纹、错误码全局注册表、类型状态 Builder 编译期保证、四层捕获架构、因果链+上下文帧双链传播、恢复状态机+断路器+确定性退避。未来我司全栈软件（含 no_std 嵌入式）将全面采用错误驱动开发模式。

#### 致命问题二：功能驱动而非流程驱动

| 问题维度 | 功能驱动现状 | 流程驱动目标 |
|----------|-------------|-------------|
| 解析流水线 | 各自实现 Pipeline/Stage | 统一流程引擎编排 |
| CI/CD 流水线 | GitLab CI/GitHub Actions 各自定义 | 统一流程定义和执行 |
| Agent 工作流 | LangGraph StateGraph / ReAct 各自实现 | 统一状态机 |
| 操作系统调度 | 内核调度器独立实现 | 流程引擎驱动调度决策 |
| 跨域复用 | 不可能 | 同一引擎驱动所有流程 |

**本项目的回应**：我司自研的 UPCM（Universal Process Control Model）流程引擎将统一驱动包含操作系统在内的所有相关软件。本项目中的 DAG 编排引擎、TaskOrchestrator 工作流引擎、RAG 流水线等即为 UPCM 理念的先行实践，验证了"不同领域的流程可以用统一的 DAG + 状态机模型来表达和执行"这一核心假设。

## 二、产品矩阵

本项目并非孤立存在，而是公司纯 Rust 产品矩阵的核心知识引擎层。三个项目协同构成完整的 AI 基础设施闭环，底层由 error-core 和 UPCM 两大统一基础设施贯穿：

| 项目 | 定位 | 许可证 | 核心能力 |
|------|------|--------|---------|
| **ullm** | LLM API 网关 | 开源 (MIT OR Apache-2.0) | 14 提供商/61+ 模型统一 `LanguageModel` trait、SSE 流式生命周期、工具调用闭环、推理模型感知、Portal/OAuth/JWT 认证 |

| **knowledge-infra** | DevOps 基础设施层 | 闭源 | 消息总线(NATS)、对象存储(S3/FS)、容器运行时(Docker)、Git 提供商、CI/CD 流水线、质量门禁、LSP/IDE 集成、代码管理(tree-sitter AST)、安全扫描(CVE)、制品仓库(OCI) |

| 基础设施 | 定位 | 许可证 | 核心能力 |

## 三、开源的战略定位

### 3.1 基线产品

本项目定位为**基线产品（Baseline Product）**，而非最终商业产品。它验证了以下架构决策的可行性：

- **一个数据库承载全部知识库需求**：SurrealDB 同时提供文档存储、图遍历、向量搜索三种能力
- **四层节点模型**：Document → Block → Token → Community，比任何竞品的 Chunk/Node 粒度更细
- **纯 Rust 推理管线**：GEMMA4-E4B 42 层 Transformer 完整实现，非 Python 封装
- **CQRS + Event Sourcing**：天然审计链 + 乐观锁 + 因果追踪
- **Cedar 风格 ABAC**：比 RBAC 更细粒度的访问控制

### 3.2 为自研数据库铺路

SurrealDB 引入 200+ 传递依赖，供应链无法收敛。本项目开源后：

1. 社区验证 Repository trait 接口设计的合理性
2. 自研分布式内存堆图对象数据库（LightField）继承同一接口
3. 以 drop-in replacement 方式替代 SurrealDB
4. 实现供应链从 200+ 传递依赖收敛至 0 外部依赖

### 3.3 统一基础设施的起点

长期目标是以 Rust 统一：

```
GIT + CI/CD + Rust 专项质量门禁 + 代码库管理 + 知识库管理 + 模型精确调用
```

本开源项目是这一愿景的第一个公开锚点。

### 3.4 错误驱动开发的公开实证

本项目通过 `error-core` crate 向全球展示统一错误处理的完整范式。当前世界软件生态中，错误模块的不统一是影响深远的致命问题——每个框架、每个库、每个运行时有自己的错误类型和传播机制，跨层错误追踪几乎不可能。

error-core 的核心创新：
- **四维分类指纹**：ErrorSource(15种) × Severity(4级) × ImpactScope(4级) × Recoverability(4级)
- **错误码全局注册表**：`ERR-{SRC}-{MOD}-{SEQ}_{SEV}_{IMP}` 格式，helpers 模块强制使用
- **类型状态 Builder**：9 个 PhantomData 编译期保证错误对象完整性
- **四层捕获架构**：Frontend → Gateway → Business → Infrastructure，层间传播语义不丢失
- **因果链+上下文帧双链传播**：兼顾可追溯性和脱敏需求
- **恢复状态机+断路器+确定性退避**：FNV-1a 哈希生成抖动，字节级可重现

未来我司全栈软件（含 no_std 嵌入式）将全面采用错误驱动开发模式，从 Web 服务到操作系统驱动，统一使用 error-core 的错误模型。

### 3.5 流程驱动开发的先行验证

本项目中的 DAG 编排引擎、TaskOrchestrator 工作流引擎、RAG 流水线等，是我司自研 UPCM（Universal Process Control Model）流程引擎的先行实践。当前世界软件生态中，传统软件聚焦功能实现，缺乏统一的流程引擎驱动——从解析流水线到 CI/CD，从 Agent 工作流到操作系统调度，每个领域各自实现状态机和编排逻辑，无法跨域复用。

UPCM 将统一驱动包含操作系统在内的所有相关软件，实现从"功能驱动"到"流程驱动"的范式转换。本项目验证了 UPCM 的核心假设：不同领域的流程可以用统一的 DAG + 状态机模型来表达和执行。

**error-core + UPCM 的深度协同**——错误驱动流程决策、流程驱动错误传播——构成了我司软件的两大基础设施支柱。

## 四、许可证策略

本项目采用**分层双许可策略**，兼顾 Rust 社区惯例与知识共享理念：

### 4.1 软件代码：MIT OR Apache-2.0

- **MIT**：简洁宽松，最大化采用率
- **Apache-2.0**：明确专利授权 + 报复条款，保护贡献者和使用者
- **双许可**：与 Rust 语言自身、crates.io 生态一致，是企业采用的黄金标准

适用范围：`src/`、`tests/`、`benches/`、`crates/` 下所有 Rust 源代码。

### 4.2 知识内容：CC-BY-SA 4.0

- **BY（署名）**：使用时需标注原作者
- **SA（相同方式共享）**：衍生知识内容必须以相同许可发布，防止知识封闭化

适用范围：`spec/`、`docs/`、知识图谱定义、本体文件、架构设计文档。

### 4.3 模型权重：不随代码分发

GEMMA4-E4B 模型权重通过 HuggingFaceDownloader 按需下载，用户自行接受 Google Gemma 许可证（Apache-2.0，含使用限制条款）。

### 4.4 为什么不使用 CC4.0 作为代码许可证

CC4.0（Creative Commons 4.0）是优秀的知识内容许可证，但**不适用于软件代码**：

| 维度 | CC4.0 | MIT + Apache-2.0 |
|------|-------|------------------|
| OSI 认证 | ❌ 未认证 | ✅ 均为 OSI 认证 |
| crates.io 兼容 | ❌ 不兼容 | ✅ 完全兼容 |
| 专利保护 | ❌ 无明确条款 | ✅ Apache-2.0 明确授予 |
| Rust 社区惯例 | ❌ 极罕见 | ✅ 黄金标准 |
| 企业采用 | ❌ 法务通常不批准 | ✅ 企业友好 |

### 6.3 核心护城河分析

开源暴露的是**算法实现**（Gemma4 推理、Leiden 检测、ABAC 引擎），而非**基础设施能力**。最深护城河分布在闭源产品中：

**自研数据库（LightField）**：
- 0GC 内存堆架构
- 双向相对指针
- 编译期确定内存布局（CodeFirst）
- 绕过文件系统直读 SSD
- 光通讯网络直接访问
- 内嵌完备形式化证明

**knowledge-infra（闭源 DevOps 基础设施层）**：
- 12 个可插拔基础设施 trait 的统一抽象层
- NATS 消息总线 + S3 对象存储 + Docker 容器运行时的生产级实现
- Git 提供商客户端 + CI/CD 流水线 + 质量门禁引擎
- LSP/IDE 集成 + tree-sitter AST 代码管理 + CVE 安全扫描 + OCI 制品仓库
- Feature gate 精细控制，默认零外部依赖

**ullm（开源但构成生态壁垒）**：
- 14 提供商/61+ 模型的统一 LanguageModel trait
- SSE 流式生命周期完整实现
- Portal/OAuth/JWT 多种认证体系
- 推理模型感知 + 工具调用闭环

**UPCM（闭源，规划中 — 最深护城河）**：
- 统一流程定义语言，跨域通用（解析/CI/Agent/OS/业务）
- DAG 编排引擎 + 条件分支 + 并行执行 + 暂停/恢复
- 与 error-core 深度协同：错误驱动流程决策 + 流程驱动错误传播
- 未来驱动包含操作系统在内的所有相关软件
- 从"功能驱动"到"流程驱动"的范式转换，无法被功能驱动的竞品复制

五层护城河形成"开源引流 + 闭源变现"的完整闭环：ullm 吸引 LLM 开发者、知识库系统吸引知识库建设者、error-core 展示统一错误处理范式、knowledge-infra 和自研数据库构成商业护城河、UPCM 构成最深护城河（流程驱动一切）。
